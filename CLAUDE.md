# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Detailed guidance is split by area: `frontend/CLAUDE.md` (SPA architecture, styling, roadmap canvas) and `backend/CLAUDE.md` (FastAPI services, persistence, auth, deployment) — each auto-loads when working under its directory.

## Most important thing to know

**The backend is five microservices under `services/` (questionnaire, matching, roadmap, auth, history) behind an nginx gateway on :8000, glued by Dapr sidecars (DEV-38/DEV-43): service invocation east-west, Redis pub/sub for submission persistence, Redis state store for the app's operational data (submissions, roadmap progress) — but NOT for durable account data, which stays in Supabase (see below) — full map + runbook in `docs/architecture.md`, Dapr building-block details in `docs/dapr.md`. Shared wire contracts (models, topics, config, the Dapr client, invoke-based auth dep) live in `services/common/` — change contracts THERE, never per-service.** The pre-split FastAPI monolith (`backend/app/`) was deleted at cutover; `backend/` retains only the venv (runs the service test suites: `cd services/<name> && ../../backend/venv/bin/python -m pytest tests -q`), `.env` (compose secrets source), and the Supabase migrations — see `backend/CLAUDE.md`. Supabase remains only for auth (GoTrue + `user_profiles` + the DEV-60 `user_profile_data`, all owned by auth-service) and `job_postings` reads (matching-service); the old `public.submissions`/`roadmap_progress` tables are no longer read.

**The frontend SPA submits the questionnaire to that gateway (same `:8000` base URL as the old monolith — zero frontend changes), and falls back to a client-side matcher if the backend is down.**

`frontend/src/App.jsx::handleQuizComplete` POSTs answers via `frontend/src/api.js` to `POST /api/questionnaire/submit` (base URL from `VITE_API_BASE_URL`, default `http://localhost:8000`). The backend builds a natural-language profile, queries the existing ChromaDB `job_ads` store, and returns explainable RAG-blended recommendations. If the request fails, the SPA falls back to `computeResults` in `frontend/src/data.js` and shows an "offline estimate" notice — so it still works standalone with no backend.

The recommendations response is shaped to match what `Results.jsx` already renders (`id, title, description, keySkills, icon, roadmapKey, matchPercent`) plus `score`, `score_breakdown`, `reasons`, `matched_skills`, `missing_skills`. The backend mirrors the 16 careers + weights in `services/common/data/careers.json` and the roadmaps in `services/common/data/roadmaps.json`. Both still also live client-side in `data.js` as offline fallbacks (`Roadmap.jsx` fetches `GET /api/roadmap/{id}` and falls back to `ROADMAPS`).

Implications:
- To change the careers/weights, update **both** `frontend/src/data.js` (the offline fallback) and `services/common/data/careers.json` (the live catalog). Same for roadmaps: `frontend/src/data.js` `ROADMAPS` **and** `services/common/data/roadmaps.json`. Same for questions: `frontend/src/data.js` `QUESTIONS`/`WEIGHTS`/`BONUSES` **and** `services/common/data/questions.json`+`careers.json` — the SPA fetches `GET /api/questions` on load (`Questionnaire.jsx`) and falls back to the bundled `QUESTIONS`. `showIf` is declarative (`{q, in}`, serialized as `show_if` in the JSON); new questions must be **appended** (never inserted) so a fetch resolving mid-quiz keeps indices stable. q11–q18 are pure discriminators: zero weights, signal via per-option bonuses only (q14–q17 are career-family follow-ups gated on q2's four options; q18 is linear). Adding/removing questions **or careers** changes the learned-matcher feature layout (the vector is `2·questions + 3·careers` wide, so the career count matters too) — bump `FEATURE_VERSION` in `services/matching/app/services/feature_builder.py` (`QUESTION_IDS` derives from `questions.json`, the per-career blocks from `careers.json`); the old artifact is then refused and matching falls back to the formula until retrained. `services/matching/tests/test_question_bank.py` enforces the bank's DoD: no two questions share a matching signal, every career ranks #1 for its archetype.
- To change matching signals/weights, edit `services/matching/app/services/matching_service.py`. There are **two** weight sets, both asserted to sum to 1: `FORMULA_WEIGHTS` and `PROFILE_WEIGHTS` (DEV-60 — the user's own skills take 0.20 from the two market-derived components; `questionnaire_fit` keeps its weight). The switch is `canonical_skills(profile)` being **non-empty**, NOT the profile being non-empty: `_profile_context()` returns `(has_profile, user_skills)` as two independent answers, and only `user_skills` selects the weights. A tag joins that set by surviving `_usable_text()` — i.e. by being predominantly Latin script — **not** by being in the alias map, so an unrecognized tag like `foobar` DOES select `PROFILE_WEIGHTS` (and then scores 0; see the "known wart" in `README.md`). An experience-only or all-non-Latin profile keeps `FORMULA_WEIGHTS`, because a `user_skill_match` of 0 for every career adds no discrimination while costing each career `0.10*(semantic_similarity + skill_overlap)` — which is *not* uniform, it penalizes the best-evidenced careers most. `has_profile` separately governs *labeling* (`matched_skills`/`missing_skills` and `model_version`) on both scoring paths, so such a profile still gets truthful skill lists. `PROFILE_WEIGHTS` is **formula-path only** — `_match_model()` never reads it. No profile at all ⇒ byte-identical output to the pre-DEV-60 formula, which is what makes the step skippable.
- **Self-input profile (DEV-60):** an optional step between questionnaire and results (`frontend/src/pages/Profile.jsx`, phase `profiling`). Persisted to Supabase `user_profile_data` by auth-service (`GET/PUT /api/profile`, migration `005`) — deliberately NOT the Dapr state store, see `docs/architecture.md`. It rides **inline** in the submit (`QuestionnaireSubmission.profile` → `MatchRequest.profile`), so it shapes the same request that produces the recommendations. Two effects: `common/profile_text.py` appends it to the embedding query (moving `semantic_similarity`, and reaching the learned matcher via `<career>_sem` with no retrain), and its skills earn the `user_skill_match` component. It also makes `matched_skills`/`missing_skills` mean what `Roadmap.jsx` always claimed — skills the user actually has/lacks. **English-only**, overriding the ticket's Hebrew requirement: everything it compares against is English, so non-Latin text is kept out of the embedding instead of degrading it.
- **Async guards in the SPA:** every continuation that outlives a run (profile save, questionnaire submit, history restore) re-checks whether its run is still current before writing — `App.jsx` owns that decision (`runIdRef`, plus live `phaseRef`/`answersRef`), because a child invalidating in a passive effect is always a render behind. The submit additionally re-checks the auth token from `localStorage`: `AuthContext.signOut` clears tokens **synchronously** but `setUser(null)` only lands on the next render, so React-state guards alone would let a signed-out run submit anonymously — and `claimSessions()` would then hand it to the next account on that browser.
- **Learned matcher (opt-in):** when `MATCHER_MODEL_PATH` is set (see `backend/.env.example`), `match()` scores with the artifact loaded once in the `main.py` lifespan instead of the formula — same response shape plus `model_version`; reasons come from exact linear attribution (`matcher_model.py` + `reason_builder.py`), features from the shared `feature_builder.py` (bump `FEATURE_VERSION` on layout changes; artifacts are refused on mismatch). Any model error falls back to the formula. Artifacts load through the **dispatch seam** in `services/matching/app/services/matcher.py` (DEV-88): a `Matcher` protocol (`predict_proba`, `contributions`, `feature_names`, `version`, `caveats`, `deployment`) plus a module-level `load_matcher(path)` and the `displays_own_percentages(matcher)` predicate that reads `deployment` that validates and dispatches on the artifact's `model_type` — the serving code depends on the protocol, never a concrete class, so a new model family is one new class plus one `_IMPLEMENTATIONS` entry. `load_matcher` raises `MatcherModelError` on every failure path because that is exactly what the lifespan catches to fall back to the formula. **The second family landed in DEV-94:** `matcher_nn.py` (`model_type: probability_averaged_mlp_ensemble`) serves the neural matcher — a numpy forward pass over a probability-averaged ensemble of ReLU MLPs whose depth, widths and member count are all read from the artifact, plus integrated-gradients attribution. It explains **the logit of the mean probability** (`log(mean_i softmax(z_i))/T`), because that is the logit of the distribution actually served and the place `train_models.apply_temperature` fits `T`; averaging the members' attributions would instead explain the mean of their logits, which is a different function. Step count adapts 32→512 until the relative completeness residual clears 1e-3, and a career that never clears it emits **no** model-derived reasons rather than numbers that do not sum to what they claim. That fall-through fires for **about one career in nine on the model that actually ships** — measured by DEV-97 on the real artifact at 11.7% (640 explanations) and 10.4% (1600), which is roughly five times better than the synthetic fixture DEV-94 had to use (34–61% depending on its weight scale, so the synthetic *number* was never quotable). The mechanism is unchanged: the integrand jumps at every ReLU breakpoint, so the Riemann sum is O(1/m) and the 512-step cap is short — just by less than it looked. It remains a real open accuracy/latency/tolerance trade **reserved for a human**, documented in `docs/dev-23-nn-rework-plan.md` Step 5.2 and the DEV-94/DEV-97 records in `data/scripts/README.md`; `services/matching/tests/ig_diagnostics.py --artifact <path>` regenerates the table (omit `--artifact` and it still reproduces DEV-94's synthetic numbers exactly). This is the first `services/` code that imports numpy; `backend/venv` needed it installed (it was already in `backend/requirements.txt`). **The neural artifact now exists: `data/models/matcher_nn_v1.json`, written by `data/scripts/export_nn_model.py` (DEV-97).** It carries the DEV-95 configuration (5-member `SeedEnsemble`, trunk 84→64→32→16), reproduces the recorded ship floor at drift 0, and takes ADR 0005's **split** verdict: top-2 stability 0.735 clears the hard floor, pooled ECE 0.139 **fails** the mitigable one — so `deployment.status` is `"ranking_only"`, and a caveat inside the artifact tells every consumer the percentages are uncalibrated and that every number displayed beside a recommendation is the formula's. (DEV-99 reworded that caveat from an instruction — "should fall back to the formula's" — into a description, once the fallback it asked for actually existed; leaving it imperative would have had the artifact telling users to do something the serving path had already done.) Its deployment temperature is `0.80` (fitted on ensemble-averaged OOF, so it sharpens where the linear artifact's 1.05 softens). **Its exporter folds the five training-constant features into the first layer's bias** — `NNClassifier`'s `scale_ = std + 1e-8` does *not* make a constant column standardize to zero, and copying `mean_`/`scale_` across the float32→float64 runtime change diverged by 1.03e-2 in probability; folding brings it to 3.15e-7 (`data/scripts/tests/test_export_nn_model.py`). The artifact's `temperature` divides the logits in **both** `predict_proba` and `contributions`, so attribution stays complete (sums to the logit behind the served probability) at any T. **It is non-inert in both shipped artifacts — `1.05` in the linear `matcher_logistic_v2.json` and `0.80` in the neural `matcher_nn_v1.json` — so flipping `MATCHER_MODEL_PATH` to either changes served `matchPercent`.** The rest of this paragraph is about the linear one. (It was `1.0` until the DEV-91 export fix: the exporter used to transfer Phase 3's deployment temperature, which belongs to nested-CV `logistic_tuned` whose `C` varies by outer fold, whereas the artifact serializes one fixed `C`. It now refits the temperature on OOF predictions from that exact fixed-`C` configuration, which reproduces 1.05. Ranking is unaffected either way — temperature scaling is monotone within a row — so only the displayed percentage moves.) **The current artifact `data/models/matcher_logistic_v2.json` is NOT stale — it is `features-v4`, matches `FEATURE_VERSION`, and loads fine** (proved by `test_shipped_artifact_loads_through_the_factory`). It is the calibrated alternative to the artifact now being served, not a broken one. The older `matcher_logistic_v1.json` **is** stale (6-career `features-v1`) and is correctly refused — `backend/.env` still points at it, but that value **never reaches the service that reads it**: only `services/matching/app/main.py` consults `matcher_model_path` (though `common/config.py` defines it for every service), and for `matching` compose's `environment:` key overrides `env_file:`, resolving it from the root `.env` instead. DEV-99 corrected the older wording "never reaches the services", which was the right conclusion from a false premise: measured with `docker compose config`, the value **does** reach `auth` and `roadmap` via `env_file: ./backend/.env`, and both ignore it. **ADR 0005's mitigation for a `ranking_only` artifact is implemented (2026-08-04)** — it was documented in three places and built in none until then, which is the gap DEV-99 found. `Matcher` now carries a `deployment` member; both implementations parse the block at load via the shared `parse_deployment` in `matcher_model.py`, where an **unrecognised `status` fails the load** rather than defaulting permissive (a typo must not grant an uncalibrated model permission to display its own numbers), and an **absent block means unrestricted** so `matcher_logistic_v2.json` is unaffected. For a `ranking_only` artifact `_match_model` takes `matchPercent`, `score` and `score_breakdown` from `_formula_scored` — extracted out of `_match_formula` so a career the model ranked but the formula would have dropped still gets priced — while `reasons` stay model-derived, and the model's own probability is preserved as `score_breakdown.model_probability` so the selection stays auditable. **The ADR was amended in the process:** the selected set is ordered by the *displayed* percentage, so the top row always carries the highest number, which narrows a `ranking_only` model from the ranking source to the **selection** source. Both paths sort through `_display_order`, which keys on `matchPercent` before `score` — the two round differently (`round(final, 3)` vs `round(final * 100)`), and ordering on `score` alone let a 49 print above a 50 once in 4000 randomised draws. Design, cost and closure: `docs/dev-23-flip-readiness.md`; the decision itself: `docs/adr/0005-gate-1-is-a-ship-floor.md`. **The flip happened (DEV-99, human-approved 2026-08-04): the repo-root `.env` now sets `MATCHER_MODEL_PATH=/store/models/matcher_nn_v1.json`, so the neural matcher serves.** It supplies the **selection** only — every displayed number is the formula's — so the user-visible change is *which* careers appear, not the percentages beside them. Rollback is blanking that one line and restarting `matching` + `matching-dapr` together; no code redeploy, but already-persisted submissions keep the `model_version`/`model_caveats` they were scored with, so rollback is complete forward only. **A restart alone is not enough on a stale image:** an image built before DEV-88/DEV-94 has no `matcher.py` dispatch seam, so `load_matcher` falls through to the linear implementation and the neural artifact is refused with `malformed model artifact ...: 'coef'` — which looks like a bad artifact and is actually a stale build. Use `docker compose up -d --build matching matching-dapr`, and confirm the `Learned matcher loaded: matcher-nn-v1` log line rather than assuming. **The artifact is trained on synthetic LLM-panel silver labels — prototype quality, not expert-validated**; pipeline + retraining: `docs/matching-rework-plan.md` and `docs/dev-23-nn-rework-plan.md`, scripts under `data/scripts/` (`panel_label_profiles.py` → `build_training_set.py` → `evaluate_matchers.py` / `train_models.py` → `export_model.py`, plus `sweep_variants.py` for the DEV-93 nested neural-Variant sweep, which writes `data/training/nn_rework.md` and checkpoints per experiment seed so a killed run resumes, and `sweep_round2.py` for DEV-95's round 2 — the recovered per-Variant scoreboard, the ≤6 refinements and the final ship-floor verdict, in `data/training/nn_rework_round2.md`; its `--stage report` re-renders that report from `round2_results.json` without refitting anything, and `learning_curve.py` for DEV-96's learning curve plus its two-point balance-controlled control curve, in `data/training/learning_curve.md` — a dedicated 3-fold subsampled protocol with the selected 5-member ensemble frozen and both comparators re-selected at every point, checkpointed per (point, seed) and carrying the same `--stage report`). All these scripts derive the question set from `questions.json` (never hardcode `q1..qN`), so new questions flow into synthetic profiles, archetypes, and training automatically — but a **retrain is still required** for the model to actually use them.
- The old Flask + SQLite backend (`backend/app.py`, `backend/db/`, `backend/scripts/seed.py`), the orphaned `frontend/src/pages/AdaptiveQuestionnaire.jsx`, the `start.js`/`start.sh`/`start.bat` launchers, and `SETUP.md` have been **deleted**; the Vite proxy to `:3001` in `vite.config.js` is dead config (api.js always calls the absolute base URL). `README.md` now documents the microservices stack.

## Commands

Frontend (from `frontend/`):

```bash
cd frontend
npm install
npm run dev      # dev server on http://localhost:3000
npm run build    # production build -> frontend/dist (use this to verify changes)
npm run preview  # serve the production build
```

There is no lint or frontend test runner. Verify frontend changes with `npm run build`.

Microservices stack (the live backend — full runbook in `docs/architecture.md`):

```bash
backend/venv/bin/python data/scripts/build_rag.py   # one-time: builds data/jobs/chroma (~1575 job ads)
# secrets: cp .env.example .env (APP_API_TOKEN); Supabase creds in backend/.env
docker compose up -d --build                        # 13 containers; gateway on :8000
cd services/<name> && ../../backend/venv/bin/python -m pytest tests -q   # per-service suites
```

Sidecar/app pairs share a netns — restart them **together** (`docker compose restart matching matching-dapr`).

(The pre-split monolith was deleted at cutover — `backend/requirements.txt` remains only to rebuild the test venv.)

Matcher training scripts (`data/scripts/evaluate_matchers.py`, `train_models.py`, `export_model.py`) run in a **separate, hash-pinned venv** — never `backend/venv`, whose installs would move `numpy`/`pandas` under the dataset digest:

```bash
python -m venv data/venv-training
data/venv-training/bin/python -m pip install --require-hashes -r data/requirements-training.txt
data/venv-training/bin/python data/scripts/evaluate_matchers.py   # must reproduce the recorded dataset_digest
```

Root `requirements.txt` deliberately does not reference it. The recorded digest, how to change a pin, and why the lockfile is single-platform: `data/scripts/README.md`.
