# answers/

Synthetic persona answers generated by local LLM, used for training and evaluating the field-prediction model. These are SILVER labels — LLM-generated, not expert ground truth (same caveat that applies to the career-matcher panel in `docs/matching-rework-plan.md`).

## Files

| File | Description |
|------|-------------|
| `question_bank_answered_local.csv` | ~5,760 rows of synthetic answers. Each row is one (persona × question) pair annotated with `model_answer`, `model_score_1_to_5`, `predicted_fields`, `field_scores_json`, `confidence`, `temperature`, and metadata about the run. Produced by `scripts/answer_questions_local.py`. |
| `annotation_failures.jsonl` | Questions that failed annotation (timeouts, connection errors). Each line is a JSON object with `question_id`, `target_field`, `error`, `run_id`, and `timestamp_utc`. Used to identify gaps to retry. |

## Personas

Each field is answered by `PERSONAS_PER_FIELD` (default 3) independent personas (e.g. *Senior Frontend Engineer*, *Frontend Architect*, *React Performance Specialist*), each at its own fixed temperature (`PERSONA_TEMPERATURES`, default `[0.2, 0.6, 0.9]`) — mirrors the 3-persona, per-persona-temperature panel in `data/scripts/panel_label_profiles.py`, which needed the same fix after its first iteration's single-temperature personas turned out to be near-clones (Fleiss kappa 0.93, see `docs/matching-rework-plan.md`).

**`target_field` is never forced into `predicted_fields`.** Rows generated before `prompt_version v4.0.0` did force it, which made "does the model confirm this field?" a meaningless 100% by construction. From v4.0.0 on, `predicted_fields` reflects only what the model actually returned, so `data/reports/question_bank_agreement_report.md` (see below) can honestly report per-field confirmation rates and flag coding-role bias (the same "defaults to developer roles" failure mode the career panel hit and fixed).

## Regenerating answers

```bash
python data/scripts/answer_questions_local.py                  # full run
python data/scripts/answer_questions_local.py --limit 50       # smoke test (no coverage gate)
python data/scripts/answer_questions_local.py --aggregate-only # recompute the agreement report only
# Requires a running Ollama instance (default: localhost:11434)
```

Resumable: reruns skip `(target_field, persona_id, split_type, id)` keys already present in the output CSV, so raising `PERSONAS_PER_FIELD` or fixing the prompt only generates the new/changed rows, not the whole file. The bulk of the current 5,760-row file predates the v4.0.0 fixes above (forced target-field injection, single temperature) — a full regeneration to replace those legacy rows has not been run yet; it's a deliberate, separate decision given the local-LLM compute cost.

## Validating answers

```bash
python data/scripts/validate_synthetic_output.py
python data/scripts/quick_trust_check_local.py --sample-size 20
```

Outputs go to `reports/`, including `question_bank_agreement_report.md` (confirmation-rate bias check + shared-subset Fleiss/Cohen kappa, written automatically at the end of a generation run or via `--aggregate-only`).
