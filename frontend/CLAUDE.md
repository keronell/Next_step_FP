# Frontend guidance

Loaded when working under `frontend/`. Cross-cutting invariants (dual client/server data sources, commands) live in the root `CLAUDE.md`.

The backend behind `VITE_API_BASE_URL` (default `http://localhost:8000`) is now the microservices gateway (`docs/architecture.md`) — same paths, same response shapes, so nothing in this frontend changed for DEV-43. The offline fallback story below is unchanged.

## Frontend architecture

Single page, scroll-based, sections stacked in `App.jsx`. A `phase` string in `App.jsx` is the source of truth and gates what each section renders:

```
idle → assessing → profiling → loading → results_ready
```

- `handleStart` → `assessing` (scrolls to the Assessment section)
- `handleQuizComplete(answers)` parks the answers in state and → `profiling` (DEV-60). It no longer submits — the self-input profile has to reach the matcher in the *same* request that produces the recommendations, so nothing is sent until that step resolves.
- `handleProfileComplete(profile)` → `loading`, then `await submitQuestionnaire(answers, profile)` (`api.js`); on success stores the backend recommendations, on failure falls back to `computeResults(answers)` and sets `notice='offline'`, → `results_ready`. Guards against duplicate submits. `profile` is `null` when the step was skipped or left empty, and the offline fallback ignores it entirely (`computeResults` only knows the questionnaire).
- `handleSelectCareer` sets `selectedCareer` and scrolls to the Roadmap section
- `handleLoadHistory(recommendations, careerId=null)` → `results_ready` directly from a saved submission (no questionnaire step); used by the History panel and by refresh-restore
- `handleReset` → back to `idle`

**Refresh-restore:** two mount effects in `App.jsx` rehydrate the last results view after a page reload (only while `phase==='idle'`, via `handleLoadHistory`). Logged-in users: once `authLoading` resolves, fetch `fetchMySubmissions()` and restore the most recent submission's recommendations + `selected_career`. Anonymous users: a second effect mirrors `results`/`selectedCareer` to `localStorage` (`nextstep_last_recommendations`, `nextstep_last_career`) whenever `results_ready`, clears them on `idle` (so `handleReset` wipes the restore), and the mount effect rehydrates from them when no user is present.

Sections (`frontend/src/pages/`): `Landing.jsx` (Hero), `HowItWorks.jsx`, `Questionnaire.jsx` (exported as `Assessment`), `Profile.jsx` (the DEV-60 self-input step, between Assessment and Results), `Results.jsx`, `Roadmap.jsx`, `History.jsx` (logged-in users only, below Roadmap), `AuthModal.jsx` (modal, rendered in `App.jsx` — state lifted there so `handleStart` can open it directly).

**Self-input profile (DEV-60):** `Profile.jsx` renders only at `phase==='profiling'` — three sections (Experience / Projects / Skills) with add, edit-in-place and remove, plus a shared `TagInput` for skills and per-project technologies (Enter or comma to add, comma-splitting so a pasted list lands in one go, Backspace on an empty field removes the last chip). Caps mirror `services/common/models/profile.py` so the UI stops you where the API would rather than letting you type into a 422. It prefills from `GET /api/profile` on entering the phase and saves via `PUT` on Continue — but **never blocks the flow on a failed save** (same best-effort posture as submission persistence). The feature is **English-only**: no RTL/`dir` handling, and the backend keeps non-Latin prose out of the embedding (`common/profile_text.py`). Chips deliberately drop `Badge`'s `uppercase` — skill casing carries meaning (PostgreSQL, PyTorch, C#). Each receives `phase` and renders null / a sub-view based on it (e.g. `Questionnaire` internally switches between `answering`, `review`, and `loading` screens). `History.jsx` ignores `phase` entirely — it renders whenever `user !== null`.

**Assessment gating:** The assessment is locked behind auth. `handleStart` in `App.jsx` returns early and opens the auth modal when `!user`. `Landing.jsx` (Hero CTA) and `Questionnaire.jsx` (`AssessmentStart`) show a Lock icon + "Sign in to …" button when `!user && !authLoading`; both still call `onStart` — the guard in `handleStart` does the routing. `authLoading=true` optimistically shows the unlocked state to avoid a flash for returning users.

**Adaptive branching:** the questionnaire asks an in-order *subset* of `QUESTIONS`, not all 18. A question may carry a `showIf(answers)` predicate; `visibleQuestions(answers)` filters `QUESTIONS` by it. `Questionnaire.jsx` derives `path = useMemo(visibleQuestions(answers))` and navigates that (index-based `currentQ`/`highWater`/dots/Back all index into `path`). Currently `q3`, `q9`, and the family follow-ups `q14`–`q17` are conditional on `q2` (exactly one of q14–q17 shows per user), so the path is 13–15 questions. **Invariant: a `showIf` may reference only *earlier* questions** (lower `QUESTIONS` index) — that keeps indices `0..currentQ` stable when the path recomputes mid-flow. On submit, answers are pruned to visible questions (`visibleAnswers()`), so the object handed to `handleQuizComplete` stays `{ qId: number | null }` but may omit branched-away keys. This is safe: the backend `QuestionnaireSubmission` accepts a partial map (rejects only *unknown* q-ids, requires ≥1 non-null), and both matchers treat a missing key as 0 (`answers.get(qid)` / `answers[q.id] ?? 0`).

**Auth context:** `frontend/src/contexts/AuthContext.jsx` provides `AuthProvider` (mounted in `main.jsx` wrapping `<App>`) and the `useAuth()` hook. `useAuth()` returns `{ user, authLoading, signIn, signUp, signOut }`. `user` is `{ user_id, email, username }` or `null` — `username` is the display name chosen at registration (falls back to `""` for sessions predating the username system; `Header.jsx` shows `user.username || user.email` so the nav is never blank); `authLoading` is `true` during the initial `GET /api/auth/me` rehydration on mount (prevents a "Sign In" flash for returning users). Tokens are stored in localStorage as `nextstep_access_token` and `nextstep_refresh_token`. `api.js` exposes a `_request` helper that auto-attaches `Authorization: Bearer <token>` to every fetch — no call site needs to handle this manually.

## Styling

Tailwind (`frontend/tailwind.config.js`) with a custom `cream`/`navy`/`gold` theme plus font/radius/duration tokens — reuse these tokens rather than hardcoding values. Animations use `framer-motion`; icons come from `lucide-react`.

**`components/ParticleField.jsx`** is the drifting gold/navy dot canvas behind a hero — used by `Landing.jsx` (the tall `min-h-screen` hero, default counts) and by `RoadmapPage.jsx`'s ~350px hero band, which passes a lower `count` and a `maskImage` bottom fade. It sizes itself with a `ResizeObserver` (no layout/font-loading timing assumptions) and checks `prefers-reduced-motion: reduce` **once at mount**, leaving a blank canvas when set. Its dot colors are literal `rgba` — canvas can't read the CSS-var theme tokens, so recoloring the theme won't move them.

## Roadmap layout & status colors (DEV-46/DEV-47/DEV-50/DEV-57/DEV-66/DEV-81)

Vocabulary is pinned in the root `CONTEXT.md` — **stage** (serialized as `sections` on the wire), **node**, **spine**, **rail**, **drop**. The old `trunk`/`stub` names are retired; the DEV-66 transpose would have inverted their meaning.

`Roadmap.jsx` renders stages **top-to-bottom** (DEV-66), each stage's nodes flowing **left-to-right** in a wrapping grid. This is deliberately *not* roadmap.sh's left/right zigzag — see `docs/adr/0001-vertical-stage-flow.md`; don't "fix" it into one. Per stage: a content-width navy `h-11` pill header (click to collapse), a gold **drop** to the node grid, and a second drop carrying the **spine** on to the next stage — emitted for collapsed stages too, so collapsing never breaks the thread. **Direction cues (DEV-81):** only the stage→stage drop carries a `ChevronDown` (`<Drop arrow />`); the header→nodes drop stays a plain line because that relation is containment, not sequence. On the last stage the same chevron terminates the spine — the old `isLast` special case is gone. Node order within a stage is shown as a navy `NumBadge` ordinal on the card's **top-left** corner, mirroring the completion check opposite it; it restarts at 1 per stage and is plain text (no `aria-hidden`), so the button announces as "2 HTML" and the order reaches screen-reader users, for whom the visual axis does nothing. The ordinal asserts that node order *is* learning order, which holds because roadmaps are hand-curated in `roadmaps.json` — this is one of the things the removal of LLM roadmap generation bought: generated node order was never constrained, so the badges would have presented arbitrary output as a required sequence. Ordinals are suppressed where `section.source === 'job_ads'` — the two stages `inject_requirements()` appends are ranked by demand, not sequenced, and the *absence* of a number is what says "any order" (the legend's numbered row is the only place that rule is stated). Numbering, not arrowheads-between-cards, because the row is `flex-wrap` with no row-break information in the DOM: a chevron between cards dangles into whitespace on a wrapped row, and at 390px — one node per row — there is no left-to-right axis to point along at all. **The rail trick:** node rows are `flex flex-wrap justify-center` with **no column gap** (padding lives inside each cell), so each cell's dotted top border butts against its neighbours' into one continuous rail — and a wrapped row grows its own rail for free. No row chunking, no measurement, no SVG, at any node count. Cells are `grow basis-[200px] max-w-[340px]`: they stretch to fill a full row, but the cap stops a lone wrapped node from spanning the whole canvas. ~5 per row at 1280px (every stage is one row on desktop), 3 at 768px, 1 at 390px — **there is no horizontal scrolling at any width**. **Two things this must not regress** (both were broken in review): flex-wrap + `justify-center`, *not* a CSS grid — grid tracks are allocated for the whole grid, so a partial last row hugs the left edge and its rail never reaches the centre line; and the absolutely-positioned dotted line at `left-1/2` spanning the row container, without which every wrapped row after the first floats detached from the spine (on a phone, where every node is its own row, that means *nothing* is connected). It is first in DOM and the cells are `relative`, so cards paint over it. Dotted connector ink is an explicit `TRACK_GOLD` `color-mix` const, *not* `border-gold opacity-60`: opacity on the cell would fade the card inside it. Node reveal is `framer-motion` `whileInView` + `viewport={{ once: true }}` (the stack is taller than the viewport, so a mount-time stagger would play out of sight) with a small per-stage left-to-right delay; the reveal rides the **outer** wrapper so a market-framed node fades in frame-and-all. Consequence: a full-page screenshot or print shows below-fold nodes blank — they animate on scroll, by design. `Roadmap.jsx` renders **no heading of its own** — `RoadmapPage.jsx`'s hero titles the page (`{career.title} Path`, falling back to the generic heading for an unknown `careerId`). **Gotcha:** the Tailwind color tokens are plain CSS-var strings (no `<alpha-value>`), so opacity modifiers like `bg-gold/60` silently generate nothing — use `bg-gold opacity-60` / `hover:bg-navy-light` instead. Node color encodes **status** as a single system (DEV-58): green = completed **only when the user ticks it** (`completedNodes` — so unchecking always reverts it; the green check badge on the card corner is part of this same state, not a separate gold-ring system), orange = skill gap (label matches `missing_skills`), slate = not started (everything else) — computed by `nodeStatus()`/`skillHits()` in `Roadmap.jsx`, which tokenizes and canonicalizes skill/label words (a small `TOKEN_ALIASES` map, e.g. `sql→database`, `api→rest`, `viz→visualization`) so e.g. `"SQL"` matches the `"Databases"` node. `matched_skills` deliberately do **not** color the canvas (that made green ambiguous); a node matching one instead shows a "you may already have this skill" hint in the drawer. `App.jsx` passes both `missingSkills` and `matchedSkills` (from the selected result's `missing_skills`/`matched_skills`) into `Roadmap`; offline/fallback results carry neither, so nodes default to slate unless completed. Node *type* (required/good-to-know/optional) doesn't affect card styling — every card gets the same fill: an opaque soft tint of its status color (`color-mix(in srgb, color 18%, cream)` + a 55% tint border, navy label; opaque so the spine can't show through a card sitting on it); type appears only as badges in the node drawer. A legend above the canvas explains the 3 states. The progress bar track above the canvas uses explicit `color-mix` background + thin border inline styles (per the alpha-modifier gotcha, `bg-navy/[0.1]` was a silent no-op that left the track invisible). **Market frames (DEV-59):** a node carrying a `demand` payload (the job-ad-derived nodes injected by the backend) renders *inside* a brand "market" frame + badge layered on top of its status tint — navy Flame "In demand · N%" for required, gold Star "Advantage" for nice-to-know (`DEMAND_COLORS`/`DEMAND_BADGE`/`DEMAND_LEGEND` in `Roadmap.jsx`); the drawer shows the same demand badge and the legend gains a market row. This frame system is deliberately distinct from the status tints so an in-demand skill you've completed still reads green inside its frame.
