# Roadmap access: the API checks login, the SPA checks "unlocked"

DEV-82 found roadmaps reachable without signing in, while the assessment that leads to them has been gated since `9f1c756`. We closed the gap with two *unequal* checks: `services/roadmap` requires authentication only, and `RoadmapPage.jsx` enforces the real rule — a roadmap opens only for a career the user holds a **recommendation** for (CONTEXT.md). The asymmetry is deliberate; do not "fix" it by hardening the API to match.

Mirroring the rule server-side would mean roadmap-service calling history-service on every roadmap fetch, coupling the two and putting an east-west hop on the hot path — to protect content that is not secret. The 16 curated roadmaps ship inside the JS bundle (`frontend/src/data.js`, `ROADMAPS`) as the offline fallback, so an unauthenticated party can read them regardless of what the API returns. What we are gating is the *experience* — the roadmap is the payoff for taking the assessment — not the data. That framing is what makes an authentication-only API check sufficient.

Eligibility is checked against an **uncapped** list. `GET /api/auth/my-submissions` returns only the newest 20 submissions (`HISTORY_LIMIT`), so a user who has run more than 20 assessments and whose only recommendation for a career is older than those 20 would be falsely locked out of a roadmap that is still stored. The SPA therefore gates on `GET /api/auth/recommended-careers` — the full set of career ids the user was ever recommended (a store scan, no extra cost) — and uses the capped submission history only to personalize skill gaps. A career that is unlocked but absent from the newest 20 simply renders as a plain roadmap.

Eligibility is also checked with a **bounded retry**, not a single shot. `save_submission` runs as a background task after the questionnaire response is sent, so for a moment after an assessment history has not yet indexed the submission — and a user who reloads the roadmap URL in that window would get a fulfilled-but-empty eligibility set and be locked out of a career they just earned, with nothing to re-trigger the check until a manual reload. The SPA therefore retries an empty eligibility result a small number of times before concluding "locked", riding out the persistence lag so the page self-heals in place. The cost is that a *genuinely* locked deep link waits out the retries on a spinner before showing the wall; the retry count is kept low to bound that.

The SPA also **fails open**: when the eligibility fetch errors we cannot prove the user was recommended this career, and we show the roadmap anyway. Failing closed would take the roadmap page down for every returning user whenever history-service is down, punishing people whose progress is saved and who did nothing wrong. The gate is therefore bypassable by anyone who can make history-service 503 — acceptable, because the same content is in the bundle.

A second bypass exists **in local development only**, and it is deliberate: `resolveUnlocked()` returns early on `import.meta.env.DEV`, so a signed-in developer opens any roadmap without first taking an assessment. `vite build` substitutes `false` and drops the branch — verified by a byte-identical production bundle with and without the line — so it is absent from anything shipped. It was chosen over granting the admin role this power, because dead-code elimination is a stronger guarantee than a runtime role check and it leaves `0003-admin-role.md`'s scoping intact. This narrows the gate for development; it does not revisit the decision above. The signed-out wall runs earlier and is untouched, so only `LockedPanel`'s "never recommended" door becomes unreachable in dev.

Three consequences worth knowing. An **offline submit by a signed-in user** unlocks only for the life of that page: the backend was down, so nothing was persisted, and the in-memory recommendation dies on reload — a later visit to the same `/roadmap/{id}` finds history successfully empty and locks. Fail-open covers a *failed* fetch, not a successful-but-empty one. This is not a new inconsistency, since those results were already unrecoverable on reload (`App.jsx`'s restore reads the same history), but it does mean a roadmap the user saw can be gone the next morning. Likewise, deleting a submission from History (`DELETE /api/auth/my-submissions/{id}`, reachable in-page via the account menu on the roadmap page itself) can re-lock a roadmap the user was working through, while their completed nodes stay in the Dapr state store — fail-open covers fetch *failure*, not a successful-but-empty history. That re-lock takes effect on the **next** eligibility resolution (reload or revisit), **not** in place: deleting the displayed career's sole assessment leaves the already-resolved unlock standing until then. This is deliberate and not worth wiring a delete→gate signal for. The polarity is benign — it is a brief *false-unlock* of the user's **own** bundled content, after **they** removed their own entitlement, not a false-lock of earned content like the two cases the gate exists to prevent — and yanking the roadmap out from under someone mid-session the instant they delete an old assessment would be the more hostile behavior. And because `Roadmap.jsx` falls back to the bundled `ROADMAPS` on any fetch error, a signed-in user whose token has expired sees the curated roadmap rather than a sign-in prompt; the 401 is invisible in the UI.
