# The admin role has exactly one capability, and deleting an account leaves the state store alone

DEV-62 asked for "role logic" before any admin functionality existed. A role with no privileged capability cannot be tested — nothing observable changes — so the ticket was scoped the other way round: pick one real capability, and let it define the role. That capability is **account management**: `GET /api/admin/users` lists every account, `DELETE /api/admin/users/{id}` removes one. Nothing else in the app is privileged, and **that is the finished state of DEV-62**, not a first slice of a permissions framework.

Two capabilities were rejected. Usage statistics over assessments would need a global index in the Dapr state store — only `idx:user:{user_id}` exists — and therefore a change to the submission write path, for a read-only number. Content management (careers, questions, roadmaps) would break three documented invariants at once: all three files are mirrored in `frontend/src/data.js` as the offline fallback, questions must stay append-only for index stability, and the career count is baked into the matcher's `FEATURE_VERSION`. Account management needs none of that: auth-service already holds both the GoTrue admin client and the `user_profiles` table.

The role lives in **`user_profiles.role`**, not in the JWT. `_fetch_profile()` already read that row on every token verification to resolve the username, so the role rides along in the same select at no extra cost — and because it is read per request rather than signed into a token, a demotion in SQL takes effect on the user's next call with no token to invalidate. It reaches other services through `UserResponse`, which `/internal/verify` already returns; the field is defaulted, so no other service changed. Roles are granted **only** by SQL (`update public.user_profiles set role='admin' where …`). No endpoint writes the column, which is what keeps the API free of a privilege-escalation surface — the cost is a trip to the database to make the first admin.

Enforcement is **server-side**, deliberately inverting `0002-roadmap-access.md`. There the API checks only authentication and the SPA holds the real rule, because the roadmap content ships in the JS bundle anyway and what is gated is an experience. Here the resource is other people's account data and the action is irreversible, so `require_admin` is the boundary; the hidden nav item and the `/admin` route's self-bounce are presentation. That bounce waits for `authLoading` to resolve — redirecting on `!user` alone would throw an admin off their own page on every refresh, while `getMe()` is still in flight.

**Deleting an account does not purge the Dapr state store.** Supabase cascades `user_profiles` and `user_profile_data`; `sub:{request_id}`, `idx:user:{user_id}` and `progress:{user_id}:{career_id}` survive, orphaned under a uuid that can never be authenticated as again. Purging them would mean two new `/internal/purge-user` endpoints (history and roadmap), east-west calls on a destructive path, and a partial-failure story strictly worse than the orphan: an account deleted but a purge failed. Roadmap progress has no per-user index at all — `progress:{uid}:{career}` would need a 16-career sweep or a new index. The honest consequence is that a deleted user's assessment answers and profile snapshot remain in Redis, unreachable but not erased; if retention ever becomes a requirement, purge is where to add it and this is the paragraph that will explain why it wasn't there first.

Self-deletion is refused (400). The admin's own row sits in the very list they are clicking through, and the role can only be restored with database access — so the realistic accident is worth one comparison. Deleting *another* admin stays possible: with two people on the project, an in-app path to remove a compromised co-admin is worth more than the symmetry. The list is capped at the first 100 accounts, unpaginated.
